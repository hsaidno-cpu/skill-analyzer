# SKILL ANALYZER — Universal Cloud Gateway

**Cloud runtime:** 1.2.0  
**One public base URL:** \`https://api.example.com\`  
**HTTP API:** \`POST /v1/invoke\`  
**Remote MCP:** \`POST /mcp\` using MCP Streamable HTTP  
**Authorization:** external OAuth 2.1 / OIDC issuer, validated by this service

This repository now contains a deployable service implementation. It is not deployed by a Git commit. A cloud account, public hostname, identity provider, model-provider credential, Redis instance, and deployment action are still required.

## 1. One base URL, two protocols

Both interfaces are served by one ASGI process and one public origin:

| Interface | URL | Use |
|---|---|---|
| Remote MCP | \`https://api.example.com/mcp\` | AI clients that support Remote MCP / Streamable HTTP |
| HTTP API | \`https://api.example.com/v1/invoke\` | Apps, workflows, scripts, and backend services |
| Command catalog | \`https://api.example.com/v1/commands\` | Discover canonical commands |
| Health | \`https://api.example.com/healthz\` | Public liveness check |
| Readiness | \`https://api.example.com/readyz\` | Provider readiness |
| Protected Resource Metadata | \`https://api.example.com/.well-known/oauth-protected-resource/mcp\` | MCP OAuth discovery metadata generated by the MCP SDK |

The public origin is unified. The MCP protocol and JSON API necessarily use different paths and payload contracts; they are not the same HTTP request.

## 2. Runtime request flow

1. The caller obtains an access token from the configured identity provider.
2. The caller sends \`Authorization: Bearer <access-token>\`.
3. The service validates JWT signature, issuer, audience/resource, expiry, and scope.
4. The distributed rate limiter checks the principal quota.
5. The canonical command registry resolves the command and its aliases.
6. The runtime loads the master orchestrator and the routed skill instructions from the repository.
7. The configured OpenAI-compatible model endpoint receives one analysis request.
8. The response is returned through HTTP JSON or MCP tool output.
9. A structured audit event records metadata only. Prompts, completions, tokens, and raw request headers are not logged.

The service does not launch ten independent model agents. Specialist routing is logical and is executed within the configured model call. It does not have web search, repository write, shell, or MCP-client tools unless separately implemented and authorized.

## 3. Authentication and authorization

Production mode is fail-closed. It requires an external OAuth 2.1 / OIDC provider and validates signed JWT access tokens using the provider's JWKS endpoint.

Required production settings:

- \`OIDC_ISSUER_URL\`: exact token issuer.
- \`OIDC_JWKS_URL\`: trusted JSON Web Key Set endpoint.
- \`OIDC_AUDIENCE\`: must match the audience in access tokens.
- \`MCP_RESOURCE_URL\`: exact public MCP endpoint, for example \`https://api.example.com/mcp\`.
- \`analyzer:invoke\`: required scope for analysis and the MCP tools.

The MCP SDK publishes Protected Resource Metadata at the well-known route. Clients use that metadata to discover the external authorization server. The Gateway is a resource server: it validates tokens but does not issue them, host a login page, or replace Auth0, Keycloak, Microsoft Entra ID, or another OIDC provider.

Configure your identity provider to issue JWT access tokens with:
- issuer matching \`OIDC_ISSUER_URL\`;
- audience/resource matching \`OIDC_AUDIENCE\`;
- a subject claim;
- expiry;
- \`analyzer:invoke\` in \`scope\` or \`scp\`.

For a client that only needs catalog discovery, the current service still uses the invoke scope. A future role/scope refinement can separate read-only access.

### Local development tokens

The \`DEV_BEARER_TOKENS_JSON\` setting is only available in \`APP_ENV=development\` or \`test\`. It exists for local smoke tests, not production identity. Production startup fails if development tokens are present. Never ship the example token from \`.env.example\`.

## 4. Model provider

The model adapter speaks the OpenAI-compatible Chat Completions contract. Configure:

- \`LLM_BASE_URL\`, for example \`https://api.openai.com/v1\`;
- \`LLM_API_KEY\`, stored only in a secret manager;
- \`LLM_MODEL\`, the model identifier supported by the chosen provider.

Other providers can be used when they expose the same compatible Chat Completions endpoint. A provider with a different request/response contract needs its own adapter. The model-provider key is never returned to clients or written to audit logs.

## 5. Controlled audit logging

The service writes structured JSON metadata to stdout for collection by the hosting platform's log service. Recorded fields include:
- UTC timestamp and server-generated request ID;
- pseudonymous actor fingerprint (HMAC with \`AUDIT_HASH_SALT\`);
- canonical command;
- provider/model identifiers;
- execution status, HTTP status, duration, and approximate input/output sizes;
- non-sensitive error code.

The service deliberately does not log:
- user target text, context, or constraints;
- model prompts or completions;
- access tokens, API keys, authorization headers, or cookies;
- full JWT claims or raw subject identifiers.

Log retention, access control, export, and deletion policies are configured in the cloud logging platform. The application does not claim that stdout logs are a tamper-proof audit ledger. For regulated workloads, export events to a restricted, retention-locked sink and document access governance.

## 6. Distributed rate limiting

- Development mode defaults to an in-memory fixed-window limit. This is per process and is not suitable for a horizontally scaled service.
- Production mode defaults to Redis and refuses to start without a working Redis backend.
- Redis failures fail closed with HTTP 503 instead of quietly removing the quota.

Use a private Redis service or a managed Redis provider. Restrict network access and store its connection string in a secret manager.

## 7. Run locally

Python 3.11+ is required by the current MCP Python SDK line.

~~~~bash
cp .env.example .env
# Edit .env: replace the development token, add LLM_API_KEY and LLM_MODEL.
python -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev-cloud.txt

set -a
source .env
set +a

uvicorn service.app.main:app --host 127.0.0.1 --port 8000 --workers 1 --no-access-log
~~~~

PowerShell users can set the same environment variables with the platform's environment-variable commands before starting Uvicorn.

### HTTP invocation example

~~~~bash
curl -X POST http://127.0.0.1:8000/v1/invoke \\
  -H "Authorization: Bearer replace-with-a-long-random-local-token" \\
  -H "Content-Type: application/json" \\
  -d '{
    "command": "audit",
    "target": "Example system",
    "objective": "Identify material failure modes and improvements",
    "depth": "deep"
  }'
~~~~

The response distinguishes \`MODEL_RESPONSE_RECEIVED\` from external tool execution. \`tool_execution_status\` remains \`NOT_CONFIGURED\` in this release.

### MCP client configuration

Use the Remote MCP URL:

~~~~text
http://127.0.0.1:8000/mcp
~~~~

In local development, supply the configured development bearer token manually. The placeholder issuer in development is not a real OAuth server and cannot issue tokens. Production clients should use OAuth discovery and the configured OIDC provider.

## 8. Deploy to Google Cloud Run

This service is containerized and can run on other container platforms. Cloud Run is the documented reference deployment.

Before deployment, prepare:
1. A Google Cloud project with Cloud Run and Artifact Registry enabled.
2. A custom HTTPS domain, for example \`api.example.com\`, mapped to the Cloud Run service.
3. An OIDC issuer and a registered audience/resource equal to \`https://api.example.com/mcp\`.
4. A model-provider API key and model ID.
5. A reachable managed Redis instance.
6. Secret Manager entries for the model key, Redis URL, and audit hash salt.

Build and deploy after setting the service URL and identity-provider configuration:

~~~~bash
gcloud run deploy skill-analyzer-gateway \\
  --source . \\
  --region asia-southeast1 \\
  --platform managed \\
  --allow-unauthenticated \\
  --port 8080 \\
  --memory 1Gi \\
  --cpu 1 \\
  --concurrency 20 \\
  --max-instances 10 \\
  --timeout 300 \\
  --set-env-vars APP_ENV=production,PUBLIC_BASE_URL=https://api.example.com,MCP_RESOURCE_URL=https://api.example.com/mcp,OIDC_ISSUER_URL=https://YOUR_ISSUER/,OIDC_JWKS_URL=https://YOUR_ISSUER/.well-known/jwks.json,OIDC_AUDIENCE=https://api.example.com/mcp,OIDC_ALLOWED_ALGORITHMS=RS256,LLM_BASE_URL=https://api.openai.com/v1,LLM_MODEL=YOUR_MODEL_ID,RATE_LIMIT_BACKEND=redis,RATE_LIMIT_PER_MINUTE=20,MCP_ALLOWED_HOSTS=api.example.com\\,api.example.com:*,MCP_ALLOWED_ORIGINS=https://YOUR_ALLOWED_WEB_ORIGIN \\
  --set-secrets LLM_API_KEY=skill-analyzer-llm-key:latest,REDIS_URL=skill-analyzer-redis-url:latest,AUDIT_HASH_SALT=skill-analyzer-audit-salt:latest
~~~~

Replace every placeholder and ensure the custom domain is mapped to this service. The example uses \`--allow-unauthenticated\` at the Cloud Run network edge because the service performs its own OAuth/JWT authorization. Do not remove application authentication. If your organization requires an additional Cloud IAM perimeter, configure that deliberately and verify MCP clients can satisfy both layers.

For a generated Cloud Run URL rather than a custom domain, the service resource URL and OIDC audience must be updated to the exact resulting \`https://...run.app/mcp\` URL. The custom-domain example avoids changing the audience when the underlying Cloud Run service URL is regenerated.

After deployment, check:
- \`GET https://api.example.com/healthz\` returns liveness.
- \`GET https://api.example.com/readyz\` returns readiness only when the provider is configured.
- \`GET https://api.example.com/.well-known/oauth-protected-resource/mcp\` returns the protected-resource metadata.
- \`POST https://api.example.com/v1/invoke\` rejects missing/invalid bearer tokens with 401.
- MCP clients can discover the issuer, obtain a token with the correct audience and scope, and connect to \`https://api.example.com/mcp\`.
- Redis rate limits are shared across instances.
- Cloud log entries contain metadata only, never prompt/response bodies or credentials.

## 9. Operational boundaries

- The service is cloud-portable but is not automatically deployed by GitHub Actions.
- A repository commit does not create a public endpoint, DNS record, OAuth client, provider secret, or Redis instance.
- This release uses one OpenAI-compatible model provider per deployment. Provider failover, model routing policies, tenant billing, and per-tenant data residency are not implemented yet.
- Analysis responses are model outputs, not independently verified facts. Current external research requires an explicitly configured retrieval/search subsystem.
- The service does not persist conversations or full prompts/completions. It emits metadata-only logs.
- Production rate limits require Redis or another shared limiter; memory mode is local-development only.
